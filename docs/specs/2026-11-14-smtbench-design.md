# smtbench — дизайн

Дата: 2026-11-14 · Статус: на согласовании

## 1. Зачем

Хостинг держит разные ноды под разные игры: Source, Minecraft, Rust. Для каждой ноды нужно понимать:

- насколько быстро одно ядро само по себе и одинаковы ли ядра между собой;
- что будет, если на одном физическом ядре работают два сервера (HT/SMT);
- как падает скорость сервера, когда загружаются остальные ядра: с какого числа загруженных ядер начинается просадка и насколько глубокая;
- как на AMD X3D с двумя чиплетами влияет нагрузка на свой и на чужой чиплет.

Результаты со всех нод собираются в одно место. Веб-интерфейс показывает их так, чтобы вывод понял человек без аналитического склада ума.

## 2. Цели, не-цели, анти-цели

**Цели**
- Один статический бинарник `smtbench` под linux/amd64 и windows/amd64. Тип нагрузки, длительность и прочее задаются флагами CLI.
- Тест «лесенкой» для каждого ядра. Меряются один поток и пара потоков ядра, а остальные ядра загружаются по нарастанию. Порядок загрузки учитывает чиплеты (группы L3) и сокеты.
- Отправка результата на коллектор: адрес задаётся флагом, авторизации нет.
- Коллектор `smtbench-server` — один Docker-контейнер, запускается одной командой. Внутри хранилище и веб-интерфейс.
- Простой веб-интерфейс на русском: светофор, короткие фразы, один главный график, карта ядер, сравнение нод.

**Не-цели (v1)**
- Точно эмулировать конкретные игровые серверы. Профили source/minecraft/rust — синтетические приближения.
- Авторизация, пользователи, удаление прогонов из интерфейса.
- ARM, macOS, 32 бита.
- Измерение частоты на Windows.
- Любые изменения системы: governor, турбо, привязка или приоритет чужих процессов, modprobe.

**Анти-цели (провал, даже если всё работает)**
- После выхода, Ctrl+C или падения утилиты на машине осталась нагрузка.
- Цифры молча смешаны с помехами от чужих процессов.
- Чтобы понять вывод, нужно разбираться в перцентилях и сырых таблицах.

## 3. Ограничения

- Ноды боевые. Полный прогон держит все потоки на 100% десятки минут. Время прогона выбирает оператор. Утилита показывает оценку длительности и предупреждает, если на машине уже есть нагрузка.
- На Linux частота читается через MSR (нужны root и модуль `msr`) или через perf. Если ни то ни другое недоступно, тест всё равно идёт, а частота помечается «не измерялась».
- Связи с коллектором может не быть, поэтому результат всегда сначала сохраняется в файл.
- Go 1.26, `CGO_ENABLED=0`, только amd64.

## 4. Подходы

| | Подход | Плюсы | Минусы | Решение |
|---|---|---|---|---|
| A | Клиент на Go (горячие циклы на Go и Go-ассемблере) + коллектор на Go (SQLite, встроенный UI) в одном образе | Один бинарник под обе ОС; один контейнер; измеряется время каждого тика | Больше кода, чем у скрипта | **Выбран.** Go был твоим пожеланием |
| B | bash + taskset + stress-ng, данные в InfluxDB/Grafana | Быстрее начать | Только Linux; нет замера тиков; Grafana — не «просто для людей»; несколько контейнеров | Отклонён |
| C | Клиент на C/C++ | Полный контроль над инструкциями | Две сборочные цепочки и кросс-сборка под Windows; по точности не выигрывает у Go + asm | Отклонён |

Для коллектора рассматривался вариант Postgres + отдельный фронтенд со сборкой через npm. Отклонён: лишние контейнеры и сборка ради сотен прогонов.

## 5. Модель теста — «лесенка»

**Термины.** *Ядро* — физическое ядро. *Поток* — логический CPU. У ядра с HT два потока: **A** (с меньшим номером) и **B**. Они равноправны: деления на «ядро» и «его HT-поток» в железе нет.

Для каждого тестируемого ядра выполняется по порядку:

1. **single.** Меряется поток A, поток B простаивает. Загружено k других ядер, k = 0…N−1.
2. **solo_b.** Меряется поток B, поток A простаивает, k = 0. Проверяет, что потоки ядра равноценны.
3. **pair.** Потоки A и B меряются одновременно: это два сервера на одном ядре. k = 0…N−1.
4. **final.** Повтор single при k = 0. Ловит дрейф (нагрев, фон).

Фоновые ядра крутят ту же нагрузку, что и тестируемое, чтобы инструкции конкурировали за одни и те же блоки.

**Соответствие исходному запросу**

| Исходный пункт | Где в модели |
|---|---|
| ядро без нагрузки на его поток | single, k = 0 |
| поток без нагрузки на ядро | solo_b |
| ядро при нагрузке на поток и поток при нагрузке на ядро | pair, k = 0 (оба потока меряются одновременно) |
| нагружены все, кроме тестируемого | pair, k = max |
| нагружены все остальные ядра, свой второй поток свободен | single, k = max |
| нагрузка по нарастанию, где и насколько деградирует | кривые single и pair по k |

**Параметры лесенки**
- `--bg-threads 2|1`. При 2 у фонового ядра грузятся оба потока («2 сервера на ядро»); это значение по умолчанию. При 1 грузится только поток A («1 сервер на ядро, HT не используем»).
- `--order near|far`. **near**: сначала ядра своей группы L3 (свой чиплет или сокет), затем другой чиплет того же сокета, затем другой сокет. **far** — в обратном порядке. При far есть точка «загружен только чужой чиплет»: k равно числу ядер чужого чиплета.
- `--step N`. k растёт с шагом N. Точки k = 0, k = max и граница группы L3 включаются всегда.
- `--cores 0-3,8`. Какие ядра тестировать; по умолчанию все.
- `--modes single,pair`. По умолчанию включены оба режима.

Фоновые потоки не перезапускаются между ступенями: к уже работающим добавляются новые. Тестируемый поток работает непрерывно на всех ступенях лесенки своего ядра.

## 6. Нагрузка

**Тик.** Единица работы — «тик»: фиксированная порция работы из нескольких ядер нагрузки, как один тик игрового сервера. При одной и той же версии ядер нагрузки (`kernels_version`) тик одинаков на всех машинах, поэтому число тиков в секунду можно сравнивать между нодами.

| Ядро нагрузки | Что делает | Чем похоже на игру |
|---|---|---|
| `int` | ГПСЧ, непредсказуемые ветвления, таблица в L1, целочисленные умножения | логика сущностей, AI, скрипты |
| `fp` | скалярная арифметика float64 (SSE2): позиции, скорости, sqrt, деление | физика и коллизии |
| `avx` | 256-битная AVX1 (VMULPS/VADDPS, 8 независимых цепочек), Go-ассемблер | векторная математика. Только AVX1, без AVX2/FMA, чтобы цифры были сравнимы на любом CPU с AVX |
| `mem` | случайные переходы по памяти (pointer chase) в буфере `--mem-size`, у каждого потока свой буфер | обход больших структур мира, чанков, сущностей |

**Единица.** 1 единица работы ≈ 1 мкс на эталоне: Xeon E5-2667 v2, одно ядро, без нагрузки. Константы калибруются один раз и замораживаются. Если их меняют, `kernels_version` увеличивается.

**Профили** — синтетические приближения; любую смесь можно переопределить через `--mix`.

| Профиль | Единиц на тик | mem-size |
|---|---|---|
| `int` (по умолчанию) | int 100 | — |
| `fp` | fp 100 | — |
| `avx` | avx 100 | — |
| `mem` | mem 100 | 64 МБ |
| `source` | int 50, fp 35, mem 15 | 16 МБ |
| `minecraft` | int 45, fp 10, mem 45 | 64 МБ |
| `rust` | int 35, fp 35, mem 30 | 64 МБ |

**Почему 64 МБ.** Это больше L3 обычного чиплета (32 МБ), но меньше L3 X3D-чиплета (96 МБ), поэтому преимущество 3D V-Cache видно. При буфере меньше 32 МБ разницы нет. При буфере больше 96 МБ оба чиплета уходят в RAM.

`--mix int=50,mem=40,fp=10` задаёт свою смесь; имя профиля в результате будет `custom`. `--mem-size` переопределяет размер буфера.

## 7. Что измеряется

В каждом окне для каждого измеряемого потока:

- **Тиков в секунду.**
- **Длительность тика.** p50, p99 и p99.9 по гистограмме с точностью 1–2%; таймер — RDTSC, инвариантный TSC.
- **Эффективная частота, МГц.** На Linux — APERF (MSR 0xE8) или счётчик циклов perf, приращение делится на время. На Windows не меряется.
- **Помехи.**
  - Доля времени, когда CPU занимал кто-то другой: 1 − (CPU-время потока / реальное время).
  - Занятость простаивающего соседа в режимах single, solo_b и final.

**Окно:** прогрев `--warmup` (по умолчанию 1 с), замер `--duration` (3 с), повторы `--reps` (1). Если повторов несколько, берётся медиана. Если помехи превышают `--noise-max` (3%), окно повторяется до 2 раз. Если и после этого помехи остаются, точка помечается «с помехами» и в интерфейсе показывается со значком ⚠. Перед самым первым окном нагружается первое тестируемое ядро на 5 с, чтобы процессор успел выйти на рабочую частоту.

**Время полного прогона** при значениях по умолчанию: окон на ядро 2N + 2, где N — число ядер; каждое окно 4 с.

| Машина | Ядер | Время |
|---|---|---|
| Xeon 2×8 | 16 | 16 × 34 × 4 с ≈ 36 мин |
| Ryzen 16 ядер (7950X3D/9950X3D) | 16 | ≈ 36 мин |
| 8 ядер | 8 | ≈ 10 мин |
| 5500X3D | 6 | ≈ 5 мин |

Сократить прогон можно флагами `--step`, `--cores` и `--duration`. `--dry-run` показывает план и оценку времени без запуска.

## 8. Топология

- **Linux.** Из `/sys/devices/system/cpu/cpuN/topology` берутся `physical_package_id` и `thread_siblings_list`. Из `cache/indexK` уровня 3 — `shared_cpu_list` и `size`. Узлы NUMA — из `/sys/devices/system/node/nodeM/cpulist`. Разрешённые процессу CPU берутся из `sched_getaffinity`: учитываются ограничения контейнера и cpuset.
- **Windows.** `GetLogicalProcessorInformationEx(RelationAll)` даёт ядра (с флагом SMT), кэш L3, NUMA и пакеты. Номер CPU = группа × 64 + бит. Привязка к CPU — `SetThreadGroupAffinity`.
- **Номер ядра** присваивается по наименьшему номеру его потока, как столбец CORE в `lscpu`. На Xeon под Linux ядро 0 = CPU 0+16, ядро 1 = CPU 1+17. Под Windows ядро 0 = CPU 0+1.
- **Чиплет = группа общего L3.** Если в сокете одна группа L3, интерфейс пишет «сокет N». Если групп несколько — «чиплет N». Группа, у которой L3 больше, чем у остальных, помечается «большой L3». Признак определяется по размеру кэша, а не по названию модели.
- **Расстояние между ядрами:** 0 — одна группа L3; 1 — один сокет, но разные группы L3; 2 — разные сокеты.
- **Ядра с одним потоком** (HT выключен, E-ядра, ограничение cpuset) тестируются без режимов solo_b и pair.

## 9. CLI

```
smtbench topo [--json]               показать ядра, потоки, чиплеты и сокеты
smtbench profiles                    список профилей и их смесей
smtbench run [флаги]                 тест
smtbench send FILE --to URL          повторно отправить сохранённый результат
smtbench version
```

| Флаг `run` | По умолчанию | Смысл |
|---|---|---|
| `--profile` | `int` | int, fp, avx, mem, source, minecraft, rust |
| `--mix` | — | своя смесь, например `int=50,mem=40,fp=10` |
| `--mem-size` | из профиля | `16MB`, `64MB`, `1GB` |
| `--duration` / `--warmup` | `3s` / `1s` | длительность замера и прогрева одного окна |
| `--reps` | `1` | повторы окна, берётся медиана |
| `--cores` | все | например `0-3,8` |
| `--modes` | `single,pair` | |
| `--step` | `1` | шаг лесенки |
| `--order` | `near` | `near` или `far` |
| `--bg-threads` | `2` | `2` или `1` |
| `--noise-max` | `3` | порог помех, % |
| `--label` | имя хоста | как нода будет называться в интерфейсе |
| `--out` | `smtbench-<label>-<дата>.json` | куда сохранить результат |
| `--send` | — | адрес коллектора, например `http://10.0.0.5:8080` |
| `--dry-run` | — | показать план и оценку времени, тест не запускать |

**Коды выхода:**
- 0 — успех;
- 1 — ошибка;
- 2 — тест прошёл, но отправка не удалась (файл сохранён, утилита печатает команду для повторной отправки);
- 130 — тест прерван (сохранён частичный результат с `partial: true`).

**Перед стартом** утилита:
- показывает топологию и оценку времени;
- проверяет, хватит ли памяти (число потоков × mem-size);
- проверяет AVX, если он нужен профилю;
- предупреждает, если фоновая загрузка машины больше 10%.

**Во время прогона** выводится строка прогресса: ядро, режим, k, тиков/с, %, ГГц, оставшееся время.

**После прогона** печатаются сводка по-русски, путь к JSON и ссылка на страницу прогона в коллекторе.

## 10. Формат результата

JSON, `schema_version = 1`:
- метаданные: `run_id`, label, hostname, os, `tool_version`, `kernels_version`, время начала и конца, `partial`;
- CPU: модель, вендор, флаги, источник частоты, логические CPU, группы L3;
- параметры запуска;
- точки: ядро, режим, k, какие CPU были загружены, сколько из загруженных ядер вне своей группы L3, результаты по потокам, помехи;
- предупреждения.

Сводка в файле не хранится. Её считает пакет `summary` из сырых точек; он общий для CLI и сервера. Если формулы изменятся, старые прогоны пересчитаются без перезапуска теста.

## 11. Коллектор

- Один Go-бинарник. Данные — в SQLite (`modernc.org/sqlite`, без CGO) в `/data`. Интерфейс встроен через `go:embed`. Графики рисуются собственным небольшим SVG-компонентом, без внешних библиотек и CDN: ноды могут быть во внутренней сети.
- API:
  - `POST /api/runs` — принимает gzip, до 32 МБ. Повторная отправка того же `run_id` не создаёт дубль.
  - `GET /api/runs`
  - `GET /api/runs/{id}` — сырой результат и сводка.
  - `GET /healthz`
  - `GET /download/smtbench-linux-amd64` и `GET /download/smtbench-windows-amd64.exe` — клиентские бинарники, собранные в том же образе.
- Авторизации нет, поэтому коллектор нужно ставить во внутреннюю сеть.
- Запуск: `docker compose up -d`, затем открыть `http://<хост>:8080`.

## 12. Веб-интерфейс

Русский язык, простые слова, светофор (зелёный / жёлтый / красный). Слова «перцентиль» и «p99» на главных экранах не появляются.

1. **Прогоны.** Таблица:
   - метка, процессор, профиль, дата;
   - две цветные цифры: «1 сервер на ядро при полной загрузке» и «2 сервера на ядро»;
   - галочки, чтобы выбрать прогоны и нажать «Сравнить».
2. **Прогон.**
   - Шапка.
   - Карточки-итоги.
   - График лесенки: скорость в % по числу загруженных других ядер. Линии «1 сервер на ядро» и «2 сервера на ядро», пунктиром — частота. Граница «дальше — другой чиплет/сокет» отмечена полосой. Над графиком переключатель «в среднем по ядрам / ядро N».
   - Карта ядер, сгруппированная по сокетам и чиплетам, с подписью размера L3. Цвет ячейки — по выбранной метрике. Клик по ядру показывает его на графике.
   - Свёрнутая подробная таблица.
3. **Сравнение 2–4 прогонов.**
   - Колонки по нодам: скорость ядра относительно первой ноды, HT, полная загрузка, лаги.
   - Общий график средних кривых.
   - Предупреждение, если у прогонов разные профиль, смесь, mem-size, длительность, bg-threads, order или версия ядер нагрузки.
4. **Как запустить тест.** Готовые команды для Linux и Windows: скачать бинарник с этого коллектора и запустить с `--send` на него. Адрес коллектора подставляется автоматически.

Набросок страницы прогона:

```
┌ node-mc-07 · Xeon E5-2667 v2 ×2 · профиль minecraft · 14.11.2026 ────────┐
│ ● 1 сервер на ядро, машина загружена целиком: 86% скорости               │
│ ● 2 сервера на одном ядре: каждый получает 58%, ядро в сумме даёт 116%   │
│ ● Лаги при полной загрузке: самые долгие тики в 2,1 раза длиннее         │
│   Просадка меньше 5%, пока загружено не больше 6 других ядер            │
├ Как падает скорость, когда загружаются остальные ядра ──────────────────┤
│ 100% ━━━━━━━━━━╲___________            ── 1 сервер на ядро               │
│  60% ━━━━━━╲_______________            ── 2 сервера на ядро              │
│      0     4      7▐8     12    15     ▐ дальше — другой сокет           │
├ Карта ядер ─────────────────────────────────────────────────────────────┤
│ Сокет 0 · L3 25 МБ   [0][2][4][6][8][10][12][14]                         │
│ Сокет 1 · L3 25 МБ   [1][3][5][7][9][11][13][15]                         │
└──────────────────────────────────────────────────────────────────────────┘
```

**Формулы сводки** (для ядра: A — первый поток, B — второй; TPS — тиков в секунду):
- база ядра: `baseA` = среднее TPS в режимах single при k = 0 и final (замер в начале и в конце лесенки ядра; турбочастота на живой машине между ними гуляет); `baseB` = TPS в режиме solo_b;
- скорость ядра (насколько оно сильное) = `baseA` / медиана `baseA` по всем ядрам; ядро ниже 95% помечается как «слабое ядро»;
- 2 сервера на ядро, на сервер = среднее из TPS(pair, k=0, A)/`baseA` и TPS(pair, k=0, B)/`baseB`;
- ядро в сумме = (TPS(pair, k=0, A) + TPS(pair, k=0, B)) / `baseA`;
- кривая single(k) = TPS(single, k, A) / `baseA`; кривая pair(k) — среднее по потокам, как выше;
- полная загрузка = значение кривой при k = max;
- лаги = p99 тика в режиме pair при k = max / p99 в режиме single при k = 0. Для пары берётся худший из двух потоков, затем среднее по ядрам;
- «просадка начинается после» = наибольшее k, при котором средняя кривая single ≥ 95%;
- дрейф = |final − single(k=0)| / single(k=0) > 3%. Все такие ядра перечисляются в одном предупреждении. Если у них же отличается частота, причиной названа частота (турбобуст);
- частота(k) = МГц(single, k) / МГц(single, 0). Рисуется на той же оси процентов, что и скорость: второй оси на графике нет;

**Пороги светофора** (предложены мной, правятся константами в коде):

| Метрика | Зелёный | Жёлтый | Красный |
|---|---|---|---|
| 1 сервер на ядро, полная загрузка | ≥ 90% | 75–90% | < 75% |
| 2 сервера на ядро, пустая машина, на сервер | ≥ 70% | 55–70% | < 55% |
| 2 сервера на ядро, полная загрузка, на сервер | ≥ 65% | 50–65% | < 50% |
| Лаги (во сколько раз дольше) | ≤ 1,5× | 1,5–3× | > 3× |

## 13. Решения, принятые мной (проверь)

1. Одна модель-лесенка вместо отдельных сценариев. Исходные пункты — точки на ней (таблица в разделе 5).
2. `--bg-threads 2` и `--order near` по умолчанию.
3. Профиль по умолчанию — `int`. Смеси профилей и `mem-size` = 64 МБ / 16 МБ подобраны мной как приближения.
4. AVX — только AVX1, чтобы цифры были сравнимы между поколениями CPU. AVX2, FMA и AVX-512 не используются.
5. Один профиль за запуск. Чтобы проверить ноду под другую игру, тест запускается ещё раз.
6. Пороги светофора — из таблицы выше.
7. Коллектор раздаёт клиентские бинарники и показывает страницу «Как запустить тест».
8. Удаления из интерфейса нет: без авторизации любой мог бы стереть данные.
9. Тики измеряются через RDTSC. Если инвариантного TSC нет, используется системный таймер и выводится предупреждение.

## 14. Проверка

- Парсеры топологии проверяются на фикстурах: реальный sysfs с Xeon E5-2667 v2, синтетический двухчиплетный 16-ядерный X3D (96 + 32 МБ L3), буфер GLPIEx с локального Ryzen 5 5500X3D (Windows).
- Реальные прогоны: Xeon (Linux) и локальный 5500X3D (Windows), отправка в коллектор, поднятый в локальном Docker.
- **Двухчиплетный путь до первого запуска на реальной X3D-ноде проверен только фикстурой.** После первого реального прогона нужно сверить разметку чиплетов с `lscpu` / hwloc.
