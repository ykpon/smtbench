# smtbench

Тест производительности ядер и потоков (HT/SMT) под нагрузкой для нод с игровыми серверами.

Для каждого физического ядра утилита меряет скорость одного потока и пары потоков ядра, пока остальные ядра загружаются по нарастанию. По результату видно:

- одинаковы ли ядра;
- сколько теряет каждый из двух серверов на одном ядре;
- с какого числа загруженных ядер начинается просадка и насколько она глубокая;
- как влияет загрузка своего и чужого чиплета (AMD X3D) или сокета.

Результаты отправляются на коллектор с веб-интерфейсом.

## Коллектор

```
docker compose up -d
```

Интерфейс откроется на `http://<хост>:8080`. Другой порт: `SMTBENCH_PORT=18080 docker compose up -d`. Данные хранятся в томе `smtbench-data` (SQLite).

Авторизации нет, поэтому ставьте коллектор только во внутреннюю сеть.

Коллектор раздаёт клиентские бинарники:

- `/download/smtbench-linux-amd64`
- `/download/smtbench-windows-amd64.exe`

Готовые команды для запуска есть на странице «Как запустить тест».

## Клиент

Linux, под root: от root нужно только чтение частоты через MSR, без root частота не измеряется.

```
curl -fsSLo smtbench http://<коллектор>:8080/download/smtbench-linux-amd64 && chmod +x smtbench
sudo ./smtbench run --profile minecraft --label node-mc-01 --send http://<коллектор>:8080
```

Windows (PowerShell):

```
iwr http://<коллектор>:8080/download/smtbench-windows-amd64.exe -OutFile smtbench.exe
.\smtbench.exe run --profile rust --label node-rust-03 --send http://<коллектор>:8080
```

Тест держит все потоки машины на 100% (полный прогон на 16 ядрах идёт около 52 минут). Игровые серверы на ноде в это время будут тормозить, а их нагрузка исказит результат. Флаг `--dry-run` показывает план и оценку времени без запуска.

### Команды

| Команда | Что делает |
|---|---|
| `smtbench topo [--json]` | ядра, потоки, чиплеты и сокеты |
| `smtbench profiles` | профили нагрузки |
| `smtbench run [флаги]` | тест |
| `smtbench send FILE --to URL` | отправить сохранённый результат |
| `smtbench version` | версия |

### Флаги `run`

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--profile` | `int` | int, fp, avx, mem, source, minecraft, rust; несколько через запятую или `all` |
| `--mix` | — | своя смесь вместо профиля, например `int=50,mem=40,fp=10` |
| `--mem-size` | из профиля | буфер памяти на поток: `16MB`, `64MB`, `1GB` |
| `--duration` / `--warmup` | `3s` / `1s` | замер и прогрев одного окна |
| `--reps` | `1` | повторы окна, берётся медиана |
| `--cores` | все | какие ядра тестировать, например `0-3,8` |
| `--modes` | `single,solo_b,pair,stability` | что мерить: 1-й поток ядра один, 2-й поток один, оба потока вместе, тест тикрейта. `single,pair,stability` на треть быстрее: 2-й поток в одиночку меряется только на пустой машине. `stability` — только тест тикрейта |
| `--step` | `1` | шаг нарастания нагрузки, в ядрах |
| `--order` | `near` | `near`: сначала свой чиплет/сокет, `far`: сначала чужой; `near,far` — оба |
| `--bg-threads` | `2` | сколько потоков грузить у соседних ядер: `2` — оба, `1` — один, `auto` — так же, как у тестируемого (один поток в замерах одного потока, два в замерах обоих); можно несколько через запятую |
| `--noise-max` | `3` | порог помех от других процессов, % |
| `--tickrate` | `64`, для minecraft `20` | тест тикрейта: тиков в секунду |
| `--tick-load` | `50` | тест тикрейта: сколько процентов бюджета тика занимает работа сервера при непрерывной нагрузке |
| `--stab-duration` | `10s` | тест тикрейта: длительность одного сценария |
| `--label` | имя хоста | имя ноды в интерфейсе |
| `--out` | `smtbench-<label>-<дата>.json` | файл результата |
| `--send` | — | адрес коллектора |
| `--dry-run` | — | показать план без запуска |

### Несколько вариантов за один запуск

У `--profile`, `--bg-threads` и `--order` можно указать несколько значений через запятую. Тест пройдёт по разу для каждого сочетания:

```
sudo ./smtbench run --profile all --bg-threads 1,2,auto --send http://<коллектор>:8080
```

Здесь 7 профилей × 3 значения = 21 полный прогон, время умножается на столько же. `--dry-run` покажет все варианты и общую оценку. Каждый вариант сохраняется в свой файл (`smtbench-<label>-<профиль>-bg<N>-<дата>.json`, с `--out r.json` — `r-<профиль>-bg<N>.json`) и отправляется сразу, как закончится. После Ctrl+C текущий вариант сохраняется как прерванный, остальные пропускаются. В конце печатается таблица всех вариантов, а в веб-интерфейсе варианты одного запуска переключаются вкладками на странице прогона. Профиль `avx` в `--profile all` пропускается, если процессор не поддерживает AVX.

### Коды выхода

| Код | Значение |
|---|---|
| 0 | успех |
| 1 | ошибка |
| 2 | тест прошёл, отправить не удалось; файл сохранён, команда для повторной отправки напечатана |
| 130 | тест прерван; сохранён частичный результат |

## Что меряется

Работа идёт «тиками»: фиксированными порциями синтетической нагрузки.

| Нагрузка | Что делает |
|---|---|
| `int` | ветвистый целочисленный код |
| `fp` | скалярная арифметика с плавающей точкой |
| `avx` | 256-битный AVX1 |
| `mem` | случайный обход буфера памяти |

Одна единица нагрузки занимает около 1 мкс на эталонном Xeon E5-2667 v2. Профили `source`, `minecraft` и `rust` — синтетические смеси этих нагрузок, а не реальные серверы.

Для каждого окна записываются:
- тики в секунду;
- длительность тика (медиана, 99-й и 99,9-й перцентили);
- эффективная частота: на Linux через APERF или perf;
- помехи от других процессов.

Если помехи выше `--noise-max`, окно повторяется до двух раз, затем точка помечается.

### Тест стабильности тикрейта

Идёт после основного теста, около минуты. Сервер работает как игровой: `--tickrate` раз в секунду делает тик и спит до следующего. Работа тика подобрана так, чтобы при непрерывной нагрузке на пустой машине занимать `--tick-load` процентов бюджета (при 64 тиках бюджет — 15,6 мс). Тик, начатый с опозданием на половину бюджета и больше, занимает следующий слот, а пропущенный слот теряется: так проседает FPS у сервера Source или TPS у Minecraft.

Сценарии:

| Сценарий | Что работает |
|---|---|
| один сервер на пустой машине | сервер на 1-м потоке первого тестируемого ядра |
| по одному серверу на ядро | серверы на 1-м потоке каждого ядра |
| второй поток ядра загружен на 100% | то же, вторые потоки загружены непрерывно |
| по два сервера на ядро | серверы на обоих потоках каждого ядра |
| все остальные потоки загружены на 100% | серверы на 1-х потоках, все остальные потоки машины загружены |
| остальные потоки то загружены, то простаивают | то же, но нагрузка включается и выключается на случайные 0,1–1 с |

Для каждого сценария записываются:
- тикрейт: средний, худшая секунда самого медленного сервера, 1% low;
- время тика в процентах бюджета: среднее, 1 из 100, самый долгий;
- доля тиков, не уложившихся в бюджет;
- var — разброс интервала между тиками;
- помехи — доля времени, когда сервер не спал, но процессор занимали другие процессы. Сценарий с помехами выше `--noise-max` помечается: его цифры хуже, чем дало бы одно железо. На живой ноде результаты теста тикрейта заметно меняются от прогона к прогону.

На Linux поток спит через `nanosleep`. На Windows сон опаздывает до 1 мс, поэтому последнюю миллисекунду перед тиком поток ждёт активно.

## Сборка

```
go test ./...
go build ./cmd/smtbench
go build ./cmd/smtbench-server
```

Нужен Go 1.26. Поддерживаются только linux/amd64 и windows/amd64.
